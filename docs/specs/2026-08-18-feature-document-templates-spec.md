# Objective Spec: Checkable Feature Document Templates

Date: 2026-08-18
Status: DONE
Approval source: GitHub issue #130 and the user's implementation request

## 1. Problem and desired outcome

- **Context:** Initialization currently gives all four feature documents the
  same placeholder body. The runtime can only distinguish a missing PRD by its
  digest and cannot identify an untouched template or a missing required
  section.
- **Outcome:** Initialization emits four deterministic, purpose-specific
  Markdown templates whose required headings are defined once in the runtime.
  The pure requirement gate receives observed PRD structure and distinguishes
  missing, untouched, incomplete, and complete documents.

## 2. Scope

### In scope

- Publish the filename, title, required headings, authoring guidance, and exact
  bytes for each feature document from one runtime module.
- Keep authoring guidance in each copied document as Markdown comments so it
  helps authors without becoming rendered document content.
- Keep templates as TypeScript literals so `skeletonEffects` remains pure by
  inspection and introduces no runtime file reads.
- Add filled fixtures for the PRD, design, tasks, and summary documents.
- Observe the active PRD once in the composition layer and pass a closed fact
  to the gate evaluator.
- Add stable reason codes for an untouched PRD and a missing required section,
  while preserving `gate.prd_ausente` for a missing document.
- Document compatibility, state, and security impact and capture verification
  evidence.

### Out of scope

- The 5 Whys and 5W2H method and machine-readable discovery record (#131).
- Acceptance-criterion identifier grammar and checkbox ownership (#132).
- Approval, digest, persisted state, or schema changes.
- Validation of design, task, or summary completeness at workflow gates.

## 3. Acceptance criteria

- [x] Each generated feature template has exact, tested bytes and valid
  Markdown with host-neutral guidance.
- [x] Required section names are declared once and consumed by template
  generation, PRD inspection, and tests.
- [x] Initialization remains deterministic and a second initialization produces
  an empty mutation plan.
- [x] The requirement gate table-tests missing, untouched, partially written,
  and complete PRDs with distinct stable reason codes and a named missing
  section.
- [x] Gate evaluation performs no I/O; PRD content is read only during runtime
  observation.
- [x] Filled fixtures demonstrate all four document structures.
- [x] Narrow tests and `npm run verify` pass with zero failures.

## 4. Test strategy and failure modes

- Unit-test exact generated bytes for all four templates and the canonical
  required-section declarations.
- Retain the existing sealed clock/randomness determinism test and init-twice
  integration test.
- Unit-test PRD inspection for missing, exact template bytes, absent headings,
  heading-like text inside code fences, and completed content.
- Table-test the pure gate evaluator for the four required PRD states.
- Add fixture-shape tests to prove each filled fixture carries every required
  heading and differs from the untouched template.
- Run formatting, spelling, English, lint, type checking, all tests, coverage,
  mutation, compatibility, build, package, and benchmark checks through
  `npm run verify`.

## 5. Compatibility and risk

- **Compatibility:** Additive reason-catalog revision only. Existing reason
  codes, schemas, digests, generated paths, and persisted state remain intact.
- **State impact:** Existing initialized projects are not rewritten unless the
  user runs initialization; feature documents remain ordinary Markdown files.
- **Security impact:** No new I/O authority or host-specific behavior. Reading
  the active PRD uses the existing project-relative durable filesystem port.
- **Primary risks:** Markdown heading parsing could accept fenced examples or
  reject harmless formatting. The inspector therefore recognizes exact ATX
  headings outside fenced code blocks and reports required names verbatim.

## 6. Ordered implementation tasks

1. Add failing tests for canonical templates, filled fixtures, PRD inspection,
   and the four gate outcomes.
2. Implement the centralized feature-document contract and switch skeleton
   generation to it.
3. Observe PRD content in composition and pass the inspection fact into the
   pure gate evaluator.
4. Publish the additive reason-catalog revision and update contract references.
5. Update architecture and verification documentation, then run the complete
   evidence suite.
