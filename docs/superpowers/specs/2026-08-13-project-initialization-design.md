# Idempotent Project Initialization and Stack Profiling Design

Issue [#25](https://github.com/thiagocorreanet/mestre-yoda/issues/25)
(`SDD-01`). Epic
[#24](https://github.com/thiagocorreanet/mestre-yoda/issues/24). Depends on
[#17](https://github.com/thiagocorreanet/mestre-yoda/issues/17) (`RUN-02`),
[#18](https://github.com/thiagocorreanet/mestre-yoda/issues/18) (`RUN-03`),
[#19](https://github.com/thiagocorreanet/mestre-yoda/issues/19) (`RUN-04`),
[#20](https://github.com/thiagocorreanet/mestre-yoda/issues/20) (`RUN-05`), and

## Problem

Every runtime capability so far has been foundation: boundaries, routing,
discovery, schemas, transactions, events, locks, previews. None of them writes
anything a user asked for. `init` is the first command that does, and it writes
into a directory the user already lives in.

That is the whole difficulty. Initialization touches `CLAUDE.md` and
`AGENTS.md` — files a person may have written by hand and cares about — and it
creates roughly two dozen files under `.brain`, `.claude`, and `.codex`. Run it
twice and nothing should change. Run it on a project that already has content
and nothing of theirs should be lost. Interrupt it halfway and the project
should be either untouched or complete, never half-initialized.

## Goals

- Establish the managed `.brain`, `.claude`, and `.codex` surfaces in one
  atomic transaction.
- Produce byte-identical output for identical inputs, so a second run decides
  there is nothing to do rather than rewriting what is already right.
- Merge into pre-existing user files only through a delimited managed section,
  and refuse rather than guess when there is no safe place to put it.
- Profile the stack from repository evidence, deterministically and offline.
- Keep the plugin runtime outside the project.

## Non-goals

- No `--dry-run` flag. See **The dry-run surface**.
- No interactive prompting inside the runtime. See **Answers**.
- No per-feature or per-run paths. `.brain/02-features/<feature>/**` and
  `.brain/**/runs/<run>/**` belong to `SDD-02` and later.
- No parity credit for `init`. See **What parity this can and cannot claim**.

## The frozen surface

The `go-v3-v0.6.5` inventory freezes `init` as a command with exactly seven
flags: `--answers`, `--detect-root`, `--force`, `--host`, `--merge`, `--root`,
and `--worktree-local`. It freezes one input contract, `stdin.init-answers`,
and it freezes the generated file inventory.

Of the 46 frozen generated files, the ones initialization owns are the skeleton:

```text
.brain/00-business/README.md
.brain/01-architecture/README.md
.brain/01-architecture/adr/.gitkeep
.brain/01-architecture/stack-profile.md
.brain/02-features/README.md
.brain/02-features/_template/{00-prd,01-design,02-tasks,03-summa}.md
.brain/02-features/_template/state.json
.brain/02-features/active
.brain/03-memory/.cache/feature-create.json
.brain/03-memory/{decisions.log,gotchas.md,task_log.jsonl,task_metrics.md}
.brain/config.json
.brain/guardrails.json
.claude/settings.json
.codex/agents/{code-implementer,implementation-evaluator,prd-researcher,spec-planner,spec-reviewer}.toml
.codex/config.toml
AGENTS.md
CLAUDE.md
```

The remaining frozen paths contain a `<feature>` or `<run>` segment and are
created by the commands that own those lifecycles.

This list is the allowlist. A destination outside it is refused with
`guard.outside_allow` rather than written, which is what keeps "only
allowlisted project files" a property of the code instead of a promise in a
document.

## One transaction

Initialization builds one `EffectPlan` and commits it through `applyPlan`.
There is no partial init to recover from: the managed transaction boundary
already guarantees that a crash leaves the project either untouched or
complete, and `RUN-05` already proved that across 220 injected fault
boundaries.

This also settles the "interrupted init" test case. It is not a new code path
to design; it is the existing recovery contract observed through a new caller.

## Idempotency is a consequence, not a feature

`normalizeManagedMutationPlan` already collapses a plan whose effects the
project already satisfies into `noop`. A second `init` with the same answers
therefore decides that nothing needs doing — provided the generated bytes are
identical.

That proviso is the actual work. Every generated file must be a pure function
of the answers, the detected stack, and the contract version. No timestamp, no
generated identifier, no map iteration order, no locale-dependent sort may
reach the output. Where a file needs to record when it was created, the value
comes from the answers or from the state contract, never from the clock.

The test that matters is not "init twice succeeds" but "the second init
reports `noop`". The first passes even when every file is rewritten with
identical-looking content; only the second proves nothing moved.

## Managed sections

`CLAUDE.md` and `AGENTS.md` are the two destinations a user may already own.
Initialization writes its content between explicit markers:

```text
<!-- BEGIN MESTRE YODA MANAGED SECTION -->
...generated instructions...
<!-- END MESTRE YODA MANAGED SECTION -->
```

Three cases, three answers:

| The file | Behavior |
| --- | --- |
| Does not exist | Written with the managed section as its whole content |
| Exists and contains the markers | The section between them is replaced; everything outside is preserved byte-for-byte |
| Exists without markers | Refused with `guard.outside_allow`, naming the file |

The third case is where an initializer is tempted to be helpful. Appending to a
file whose structure it does not understand is how a tool silently corrupts a
document somebody wrote. `--merge` is the user's explicit statement that
appending the section is acceptable; `--force` is their explicit statement that
replacing the file is. Neither is inferred.

A managed section whose end marker precedes its begin marker, or which appears
twice, is refused as `runtime.state_corrupt` rather than repaired by guessing
which one was meant.

## Answers

The runtime does not interview anybody. It accepts one canonical answers
document, validated through the schema registry, supplied either on stdin (the
frozen `stdin.init-answers` contract) or from the path given to `--answers`.
Supplying both is a usage failure rather than a precedence rule nobody can
remember.

Keeping the interview in the host adapter is what makes initialization testable
without a terminal and identical under Claude Code, Codex, and a CI job. It
also keeps the runtime deterministic: an answers document is data, and the same
data produces the same project.

Absent answers are not prompted for. Each has a documented default, and the
result reports which defaults were applied, so a person can see what they did
not choose.

## Stack profiling

Detection is a pure function from observed repository evidence — the presence
and content of manifest files — to a profile. It performs no network access and
runs no package manager. The observation is made through the existing
`Workspace` and `Git` ports; the classification is domain code that cannot
reach a filesystem.

An unrecognized stack is a valid outcome, not a failure. The profile records
what was observed and states that no known stack matched, because a project the
tool does not recognize is still a project the tool must initialize.

## The dry-run surface

`RUN-09` delivered `previewPlan`, and initialization is the first command with
a decision worth previewing. A caller computes the init plan and previews it
with the same function that commits it.

No `--dry-run` flag ships even so. The frozen inventory lists seven flags for
`init` and none of them is `--dry-run`; the string does not appear anywhere in
the discovery inventory. `RUN-09` refused to invent it and nothing here changes
that reasoning — what changes is that the capability behind it now has a real
decision to describe.

## Result mapping

| Situation | Reason |
| --- | --- |
| The project was initialized, or already matched the answers | `trail.ok` |
| A managed destination exists without markers and no flag authorizes it | `guard.outside_allow` |
| The answers document fails validation | `contract.state_version_invalid` |
| A managed section is malformed | `runtime.state_corrupt` |
| An incomplete transaction blocks the commit | `runtime.recovery_required` |
| A destination moved between the decision and the commit | `runtime.revision_conflict` |

The result reports every destination as created, updated, or preserved. A
person needs to know which of their files the tool touched more than they need
a count.

## What parity this can and cannot claim

This is the first issue that could move parity off 0 / 400, and it should move
it carefully.

The inventory freezes the flag *names* under hash-only provenance. It does not
establish what `--merge` merged, what `--force` forced, or what the legacy
answers document contained. The semantics above are this runtime's contract,
chosen to satisfy the issue's acceptance criteria — not recovered from the
oracle.

So `init` claims parity only for what the inventory actually establishes: that
the command exists, that it accepts those seven flag names, and that it
generates those paths. Behavioral rows stay unclaimed until a differential
capture exists to compare against, which is `CMP-05` work. Claiming a
behavioral row on the strength of a name would make the parity number describe
something other than parity.

## Testing strategy

**Pure profiling.** Property tests over generated evidence sets: detection is
total, deterministic, and never rejects a project.

**Generation determinism.** The same answers produce byte-identical output
twice, asserted on the bytes rather than on a success flag.

**Idempotency.** A second `init` previews as `noop`.

**Managed sections.** All three cases, plus a malformed section, plus a file
whose content outside the markers is asserted byte-identical afterwards.

**Allowlist.** A generated destination outside the frozen list fails the test
that enumerates them, so adding a file is a deliberate act.

**Interruption.** Faults injected across the init transaction leave the project
untouched or complete, reusing the campaign shape `RUN-05` and `RUN-07`
already use.
