is claimed as TypeScript parity yet:

These totals are generated by `npm run parity:check`. Inventory completeness is
not implementation completeness: a row receives no credit merely because it is

## PRD is a P0 boundary

Four dedicated P0 rows preserve the independent frozen PRD anchors:

- `PRD-RESEARCHER` owns adaptive research and the no-write `needs_input`
  outcome;
- `PRD-OUTPUT-SCHEMA` owns completed versus blocked structured results;
- `PRD-PROBLEM-DISCOVERY` owns adaptive 5 Whys, probable root cause, and 5W2H;
- `PRD-TEMPLATE` owns the generated WHAT/WHY artifact and excludes
  implementation architecture and code.

Their legacy references are paths and identities only. The private researcher,
schema, reference, and template contents are not published. Their independent
byte counts and SHA-256 values remain in the
[frozen oracle manifest](../../compatibility/oracles/go-v3/v0.6.5/manifest.json).

## Discovery and matrix authority

The discovery snapshot answers: “What existed in the authoritative Go
release?” It is immutable for oracle `go-v3-v0.6.5`. A change is valid only when
the capture algorithm itself was proven incomplete or incorrect.

The matrix answers: “Who owns each contract, what must it do, how will it be
verified, and what evidence exists?” It evolves as later compatibility work
lands. Stable row and verification IDs are never reused or renumbered.

Each row has these mandatory fields:

| Field | Meaning |
| --- | --- |
| `id` | Stable public compatibility identifier |
| `category` and `title` | Searchable domain and behavior name |
| `legacy_refs` | Repository-relative source metadata, never private content |
| `covers` | Discovery keys owned exactly once by this row |
| `expected_behavior` | Normal, failure, and edge requirements for P0/P1 |
| `priority` | `P0`, `P1`, or `P2` |
| `typescript_owner` | Contracts, runtime, adapters, or plugin boundary |
| `verification` | Stable unit, differential, integration, and E2E cases |
| `status` | Current evidence-backed progress |
| `intentional_difference` | Approval chain or `null` |

## Evidence lifecycle

Every row names four cases from the beginning:

1. `unit` checks isolated TypeScript behavior;
2. `differential` runs the same scenario against Go and TypeScript;
3. `integration` checks interaction across the owning boundary;
4. `e2e` checks the final bundle in a clean project fixture.

A planned case has `status: planned` and `path: null`. A passed unit,
integration, or E2E case points to a nonempty `tests/**/*.test.ts` file; passed
differential evidence points to a nonempty JSON fixture below
`compatibility/fixtures/`. The file must name the row or stable verification
case, so an unrelated existing path is not evidence.

Row status progresses from `not_started` to `in_progress`, then to either:

- `parity`, only when all four cases passed and their paths exist; or
- `intentional_difference`, only when all four replacement-behavior cases
  passed and the row links an accepted ADR, migration note, replacement
  behavior, and public maintainer approval.

The checker rejects false parity, missing evidence, mismatched case IDs, stale
paths, and inactive exception data.

## Objective percentage

The calculation has no weights or subjective partial credit:

```text
credited = passed parity rows
         + fully approved and tested intentional differences
percent = credited / all rows * 100
```

The implementation uses integer basis points and renders two decimal places.
It reports overall, P0, and P1 results from the same rule. P2 remains in the
overall denominator but has no separate release-gate percentage.

## Contributor workflow

Run the offline completeness check after any catalog, compatibility test, or
evidence change:

```bash
npm run parity:check
```

When implementing a row:

1. keep its row ID and discovery coverage unchanged;
2. change status to `in_progress` while work is incomplete;
3. implement the named unit, differential, integration, and E2E cases;
4. set each case to `passed` only with its real checked-in path;
5. set the row to `parity` only after all four cases pass;
6. run `npm run verify` and record the new objective percentage.

New frozen behavior is first added to discovery with provenance and a source
cross-check, then mapped exactly once. New TypeScript-only behavior is not
silently described as Go parity; an incompatibility needs a versioned contract
and the complete intentional-difference approval chain.

## Authorized source cross-check

Public CI remains offline. An authorized maintainer can re-run mechanical
discovery against clean detached source and distribution checkouts:

```text
node scripts/check-parity-inventory.mjs \
  --source <authorized-source-checkout> \
  --dist-source <authorized-distribution-checkout>
```

The checker requires both checkouts to be clean, detached, and exactly at their
immutable commits. It then compares command metadata, `go list` packages,
schema names, tracked distribution files, workflow names, and closed
reason-code constants, and verifies every catalog reference exists in one of
the frozen trees (including any named anchor). It reports only public IDs,
counts, percentages, and pass/fail status. Caller paths and private file
contents are never printed.

For mutation testing, `--discovery <file>` and `--matrix <file>` validate
explicit catalogs. Unknown options, unpaired private checkouts, and malformed
option/value forms fail before any private input is read.

## Publication boundary

The catalogs contain names, repository-relative references, counts, immutable
identities, original behavioral summaries, and hashes only. They contain no
predecessor source, prompt, schema body, fixture payload, help prose, binary,
private clone URL, credential, absolute local path, customer data, or
confidential business payload.

All checker code, tests, matrix organization, verification IDs, behavioral
summaries, and documentation are original work. The private predecessor remains
a behavioral oracle with content publication denied until separate
MIT-compatible authority is established.
